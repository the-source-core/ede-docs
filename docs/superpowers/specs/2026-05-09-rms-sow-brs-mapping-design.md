# RMS SOW ↔ BRS Traceability Mapping — Design

**Date:** 2026-05-09
**Status:** Draft for review
**Owner:** Pricing / RMS programme
**Related artifacts:**
- `roadmap/logistics/pricing/RMS.docx.pdf` — BRS (Business Requirements Specification)
- `roadmap/logistics/pricing/RMS_SOW.docx` — SOW (Statement of Work, generated)
- `roadmap/logistics/pricing/RMS_TSD.docx` — TSD (Technical Solution Document, generated)
- `roadmap/logistics/pricing/_generate_sow_tsd.py` — generator

## Context

The RMS BRS contains ~333 stable requirement IDs (`RM-001`, `ME-001`, `CUR-001`, `OCN-001`, `CHG-001`, `BUY-001`, `SELL-001`, `CAL-001`, `MAR-001`, `PM-001`, `SRC-001`, `SR-001`, `AQ-001`, `REN-001`, `CON-001`, `SPT-001`, `UPL-001`, `VER-001`, `WF-001`, `INT-CRM-001`, `INT-QTN-001`, `INT-OPS-001`, `INT-ACC-001`, `INT-CP-001`, `INT-VP-001`, `NOT-001`, `BR-001`, plus a handful of mode-specific prefixes — `LCL-`, `AIR-`, `RD-`, `RAIL-`, `CUS-`, `WH-`) grouped under 33 thematic sections. The BRS is the contractual requirements baseline.

The RMS SOW is generated by hand-coded Python (`_generate_sow_tsd.py`) and currently has **no traceability link** back to the BRS. As phases reach acceptance, the customer must verify that every committed BRS requirement is either (a) covered by a deliverable, or (b) explicitly out of scope. Without a mapping artifact, that conversation cannot happen on a single page.

This change introduces a complete bidirectional traceability map between the SOW deliverables and the BRS Req-IDs, surfaced inline in both the SOW and TSD plus a structured appendix, and protected by a coverage assertion that prevents silent drift.

## Goals

1. Every BRS Req-ID is mapped to either a SOW deliverable or an explicit out-of-scope reason.
2. A reader of `RMS_SOW.docx` can see, on each deliverable row, which BRS Req-IDs that deliverable satisfies.
3. A reader of either document can navigate the appendix to find every BRS Req-ID and learn its disposition.
4. A future contributor cannot add or remove a BRS Req-ID without the generator failing loudly.
5. The change is reversible per phase — SOW and TSD remain re-generable from a single Python invocation.

## Non-goals

- Not changing the per-feature roadmap markdowns under `phase-1/`, `phase-2/`, `phase-3/`. Their content is unaffected.
- Not building a UI for editing the mapping. The mapping is a code artifact reviewed in PRs.
- Not deriving the mapping from the markdowns automatically. The first-cut is human-authored.
- Not introducing a new external dependency (no YAML, no DB).

## Architecture

### Module layout

```
roadmap/logistics/pricing/
├── _brs_mapping.py           # NEW — pure data + helpers
├── _generate_sow_tsd.py      # EDIT — consumes _brs_mapping
├── RMS_SOW.docx              # REGEN
└── RMS_TSD.docx              # REGEN
```

`_brs_mapping.py` is a leaf module with no dependencies on `python-docx` or anything in the EDE Framework. It is pure data + small helpers, importable by the generator and by future tooling (a CLI sanity check, a CI lint job, etc.).

### Generator changes

#### `build_sow()` — three deliverable tables

The existing tables at lines `309–322` (Phase 1), `370–383` (Phase 2), `433–446` (Phase 3) currently have columns `["#", "Feature", "Spec", "TSD §"]`. Add a 5th column **`BRS Refs`**, populated by `", ".join(DELIVERABLE_BRS[deliverable_id])`. Adjust `col_widths_cm` to fit letter-size:

| Old widths           | New widths                  |
| -------------------- | --------------------------- |
| `[1.0, 7.0, 3.0, 5.0]` | `[1.0, 5.0, 2.5, 2.5, 5.0]` |

#### `build_sow()` — new appendix `§13. BRS Traceability Matrix`

Inserted as a new `§13` immediately after the existing `§12. Sign-off`. No renumbering of existing sections. Rendered via existing `add_heading` / `add_table` helpers, prefixed with a `add_page_break()` so the appendix starts on a fresh page.

**§13.1 Forward Map** — three tables, one per phase:

```
| #     | Feature                          | BRS Refs (count: N)               |
| ----- | -------------------------------- | --------------------------------- |
| P1-D1 | Rate Master                      | RM-001, RM-002, ..., BR-013       |
```

**§13.2 Reverse Map** — single table, BRS-section-grouped, one row per Req-ID:

```
| Req ID  | Requirement (truncated 80 chars)        | Phase | Deliverable | Status         |
| ------- | --------------------------------------- | ----- | ----------- | -------------- |
| RM-001  | System shall allow creation of buy ...  | P1    | P1-D1       | In scope       |
| RM-002  | System shall classify rates by mode ... | P1    | P1-D1       | In scope       |
```

The grouping is implemented by emitting a sub-heading row before each new BRS section and not via Word grouping primitives.

#### `build_tsd()` — feature blocks + appendix

`feature_block()` (line 586) gains a new keyword-only parameter `deliverable_id: str | None = None`. When supplied, the block renders an extra paragraph immediately under the existing `Spec:` line:

```
BRS coverage: RM-001, RM-002, RM-003, ... (count: N)
```

Each existing call to `feature_block()` is updated with its corresponding `deliverable_id`. The same `§13` appendix structure (forward + reverse) is added to the TSD before the document end.

#### Coverage assertion

Both `build_sow()` and `build_tsd()` call `assert_full_coverage()` as the first statement. This means a regression — adding a BRS Req-ID without mapping it, or removing a Req-ID still referenced — fails the build with a clear message before any docx is written.

```python
def assert_full_coverage() -> None:
    catalogue_ids = {req["id"] for req in BRS_CATALOGUE}
    mapped = {rid for rids in DELIVERABLE_BRS.values() for rid in rids}
    out_of_scope = set(OUT_OF_SCOPE_REQS.keys())
    unmapped = catalogue_ids - mapped - out_of_scope
    unknown_in_scope = mapped - catalogue_ids
    unknown_out_of_scope = out_of_scope - catalogue_ids

    errors = []
    if unmapped:
        errors.append(f"Unmapped BRS IDs (add to DELIVERABLE_BRS or OUT_OF_SCOPE_REQS): {sorted(unmapped)}")
    if unknown_in_scope:
        errors.append(f"DELIVERABLE_BRS references IDs not in BRS_CATALOGUE: {sorted(unknown_in_scope)}")
    if unknown_out_of_scope:
        errors.append(f"OUT_OF_SCOPE_REQS references IDs not in BRS_CATALOGUE: {sorted(unknown_out_of_scope)}")
    if errors:
        raise RuntimeError("BRS coverage check failed:\n  - " + "\n  - ".join(errors))
```

## Out-of-scope BRS items (initial proposal)

- **§25 Reports & Dashboards** — entirely out of scope per SOW §4. (No Req-IDs in §25; reports are listed by name. Nothing to put in `OUT_OF_SCOPE_REQS`.)
- **`INT-QTN-005`** — quotation-conversion tracking is owned by the Quotation/CRM module, not RMS. RMS only emits rates.
- **`MAR-010`** — appears in two deliverables (P2-D6 predictive margin uses it, but its raw "margin variance via shipment/accounting integration" is also delivered by P3-D3). It is encoded once on P2-D6; final placement is reviewed during the first-cut.

The complete `OUT_OF_SCOPE_REQS` content is finalised when the mapping module is authored.

## Trade-offs

- **Python module over YAML/CSV.** The mapping never leaves the engineering tree — non-engineers reviewing the SOW will read the rendered `.docx`, not the source file. Python keeps lint coverage and refactor safety on the generator's side.
- **Single source of truth (`_brs_mapping.py`) over per-markdown frontmatter.** Frontmatter would scatter the data across 18 files and require a parser. A central module is one diff per change.
- **Coverage assertion as `RuntimeError` over silent `TBD`.** The customer signs the SOW; ambiguity in a contractual document is worse than a build that aborts.
- **Forward + reverse appendix in both SOW and TSD.** Same data rendered twice — but the SOW reader (commercial) and TSD reader (engineer) traverse from different starting points, and the cost is just a few `add_table()` calls.

## Verification

Manual:

```bash
python roadmap/logistics/pricing/_generate_sow_tsd.py
```

Expectations:

1. Exit code 0; both `RMS_SOW.docx` and `RMS_TSD.docx` regenerated.
2. Open `RMS_SOW.docx`:
   - §5.1, §6.1, §7.1 each have a **`BRS Refs`** column populated for every row.
   - §13 appendix present with §13.1 (three forward tables) and §13.2 (one reverse table grouped by BRS section).
   - Every BRS Req-ID from the catalogue appears once in §13.2 with a Status that is not `TBD`.
3. Open `RMS_TSD.docx`:
   - Each feature block in Phases 1/2/3 carries a `BRS coverage:` line under its `Spec:` line.
   - §13 appendix present, mirroring the SOW.

Negative test (drift detection):

```bash
# Temporarily delete one ID from DELIVERABLE_BRS
python roadmap/logistics/pricing/_generate_sow_tsd.py
# expect: RuntimeError: BRS coverage check failed:
#   - Unmapped BRS IDs (add to DELIVERABLE_BRS or OUT_OF_SCOPE_REQS): ['RM-002']
```
