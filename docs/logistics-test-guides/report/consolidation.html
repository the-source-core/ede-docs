Section 01

01What Consolidation does & how to read this guide

Consolidation is “many shipments sharing one equipment usage.” The module owns very little cargo data — it sits on top of Shipments (master + houses) and Equipment-Ops (the shared equipment.usage). It owns the console (the orchestration header + status lifecycle), the policy / type reference masters, and three computed projections: eligibility, capacity snapshot, and the mode-aware manifest.

The state machines you will observe

The console carries the governed lifecycle; two derived enums track cut-off discipline and manifest issue. Watch all three during Scenarios B and C.

console.status  : draft → planning → confirmed → frozen  |  cancelled (from draft / planning / confirmed only)
cutoff_state    : open → soft_closed → hard_closed  (soft = etd − consol.cutoff_hours_before_departure)
manifest.status : draft → generated → issued  |  superseded   ·   eligibility: eligible / eligible_with_warning / ineligible

The nine commands, grouped by scenario

Config & projections (A / C)

  • eligibility.recompute — per-shipment verdict
  • capacity.snapshot.recompute — capacity remaining
  • manifest.generate · manifest.issue
  • Pool = a saved search over consolidation.eligibility via consolidation.pool.filter

Console lifecycle (B)

  • console.set_planning — draft → planning
  • console.confirm — completeness gate + auto-master
  • console.evaluate_cutoff — recompute cut-off state
  • console.freeze · console.cancel

Section 04 · Scenario B — the guards that must hold

04Lifecycle & cut-off guards — each must refuse

Half of testing an orchestrator is confirming it refuses out-of-order transitions and past-cut-off freezes. Each row trips a real ValueError — the quoted text is the exact message from the command handler. Use a fresh console (or reset the demo one) so each guard is reached cleanly.

#ActionExpected refusal (exact message)✔Trace
1confirm a console still in draft (skip set_planning).“cannot confirm a console in status 'draft' (allowed: ['planning']) — BR-CC-01”.BlockedBR-CC-01
2Move to planning, then confirm before filling POL/POD/carrier/equipment.“cannot confirm — these must be set first: pol_id, pod_id, carrier_id, equipment_type_id (BR-CC-05)”.BlockedBR-CC-05
3On a confirmed console, back-date si_cut_off (or vgm/customs) to the past, then freeze without an override.“cannot freeze — these carrier cut-offs are already in the past: si_cut_off (BR-CO-05; pass cutoff_override to proceed)”.BlockedBR-CO-05
4Re-run step 3's freeze passing cutoff_override=true in the payload.Override accepted → status frozen; the past cut-off is bypassed by explicit override.Override path worksBR-CO-05
5freeze a console that is still in planning (not yet confirmed).“cannot freeze a console in status 'planning' (allowed: ['confirmed']) — BR-CC-01”.BlockedBR-CC-01
6cancel a frozen console.“cannot cancel a console in status 'frozen' (allowed: ['confirmed', 'draft', 'planning']) — BR-CC-01”. A frozen console is terminal for cancellation.BlockedBR-CC-01
