Section 01

01What Shipments does & how to read this guide

The shipment is the long-lived operational record of a cargo movement — the counterpart to the short-lived booking. It owns the journey, the parties, the cargo, the frozen charges, the routing, and the leg(s) that bind to physical equipment. One model, logistics.shipment; transport_mode_id is a field, not a subclass.

The two state machines you will observe

Shipments carry a governed lifecycle (command-driven) plus an operational projection derived from movement events. Watch both on the form header.

status     : draft → created → pending_validation → ready_for_execution → in_execution | cancelled
op.status  : not_started → in_transit → arrived → delivered → closed  (applies after in_execution)
validation: pending → passed | failed | override_approved

Two orthogonal classifications set at creation

movement_structure

  • single_mode — one mode end-to-end (demo FCL export)
  • multimodal — ≥2 legs, one carrier responsibility
  • intermodal — ≥2 legs, leg-wise responsibility

hierarchy_type

  • direct — master only, no houses (demo)
  • master / house / house_master_linked — consolidation
  • console — grouped console master

Section 03 · Scenario A

03The readiness gate & the guards that must hold

Half of testing a backbone is confirming it refuses bad input. First, the ten-condition mark_ready gate; then four negative checks that each trip a specific guard.

The ten-condition completeness gate (BTS-19/21/22)

To force a failure, clear one required field on a fresh shipment before mark_ready — the command returns ok:false with a reasons list, status parks at pending_validation, and validation_state=failed.

#Condition checkedFailure message you should see if missing
1Source booking linked“No source booking is linked”
2Shipment number generated“Shipment number not generated”
3Movement structure selected“Movement structure not selected”
4Shipment hierarchy selected“Shipment hierarchy not selected”
5Operation owner assigned“Operation owner not assigned”
6Backup owner (only if shipment.require_backup_owner on)“Backup owner required but not assigned”
7Origin — facility or place of receipt“Origin (facility or place of receipt) not set”
8Destination — facility or place of delivery“Destination (facility or place of delivery) not set”
9Mandatory party roles present; cargo min detail + hazardous completenessparty / cargo–specific reason
10Legs ≥ 2 for multimodal / intermodal (single_mode needs 1)leg-count reason — see Scenario B
Override pathA manager may pass override=true (with shipment.allow_validation_override on) to push a failing shipment through — status still flips to ready but validation_state=override_approved and the reasons are retained for audit. Confirm the override is recorded, not silently discarded.

Section 04 · Scenario B — the multi-leg deep-dive

04Multi-leg journeys — multimodal & intermodal

Goal: build a door-to-door journey out of sequenced legs and prove the engine treats a multi-mode shipment as one record with many legs — never a flat single record, and never per-mode duplicate models. Start: create a shipment with movement_structure=multimodal (or intermodal).

Leg 1 pickup (road) → Leg 2 main-carriage (sea) → Leg 3 transshipment (sea) → Leg 4 final delivery (road)
    each leg: own mode · carrier · booking-ref · planned/actual dates · equipment.usage · leg_status
#ActionExpected result✔ CheckpointTrace
1On the multimodal shipment, run mark_ready while it still has only one leg.Gate fails — a leg-count reason is returned; status parks at pending_validation.Single leg is rejected for multimodal.gate #10
BR-LEG
2Add legs with add_leg — a pre-carriage road leg and a main-carriage sea leg, each with its own carrier / booking-ref / planned dates / equipment usage.Legs appear sequenced; each holds its own mode and provider; the shipment framing mode is unchanged.≥2 legs, per-leg mode differs from framing mode.BTS-09
BR-LEG
3Add a transshipment leg and set the header transshipment_id.Re-routing via the transship port is represented as its own leg; no data overwritten on the main leg.Transship leg distinct from main carriage.BR-LEG
4Re-run mark_ready.With ≥2 legs (and other conditions met) the gate now passes → ready_for_execution.Multi-leg shipment reaches ready.BTS-19
5Attempt remove_leg without a reason.Rejected: “remove_leg requires a reason”.Reasonless removal blocked.BR-SH-99
6remove_leg with a reason, then re-check leg count vs. the structure.Leg removed & audit-logged; if the count drops below 2 the shipment would fail a subsequent readiness re-check.Removal audited; count enforced.BR-SH-99

multimodal vs intermodal

  • multimodal — ≥2 legs, one responsibility (single governing contract)
  • intermodal — ≥2 legs, leg-wise responsibility
  • Both require ≥2 legs at the readiness gate; single_mode requires exactly 1

Leg ownership (with master/house)

  • Shared main-carriage legs live on the master
  • First/last-mile legs live on the house
  • Each leg binds one equipment.usage — don't share a usage ref across legs unless intentionally consolidating
⚠ The anti-pattern to catchIf you ever see mode-specific shipment records (shipment.sea / .air / .road) or a single flat record trying to hold two modes, that is a defect — the design is one logistics.shipment + N logistics.shipment.leg rows.
