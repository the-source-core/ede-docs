Constraints & Validation
How to Enforce a Rule

A practical guide to the three tools for enforcing invariants on a business model — the two constraints.* DB declarations, the @api.constrains code decorator, and lifecycle hooks — with copy-paste examples and a decision guide.

Section 01

01Four tools, one decision

Enforcing a rule on a model is a question of where it should run. Pick the highest, cheapest tool that can express your rule.

Tool 1
Field flags
Is the shape valid?
required=True·unique=True (single field)·Char(max_length, regex)·Reference(on_delete)
Tool 2 · DB-driven
constraints.*
A guarantee the database enforces against ANY writer.
constraints.Check("min_qty <= max_qty")·constraints.Unique("code","org_id")
Tool 3 · Code-driven
@api.constrains
A business rule — conditional, cross-field, cross-record.
@api.constrains("stage","partner_id")→raise ⇒ veto
Tool 4 · Lifecycle
@api.on_hook
Op-specific: delete guards, post-write effects, raw cmd access.
@api.on_hook("pre.crm.lead.delete")·post.{model}.{op}

Which one do I reach for?

You need to…UseRuns
Require presence, single-field uniqueness, string length/pattern, FK behaviourField flags — fields.X(required=, unique=, …)DB + load
Guarantee a predicate over one row's columns (e.g. min ≤ max) that must hold against raw SQL tooconstraints.CheckDatabase
Guarantee composite uniqueness across 2+ columnsconstraints.UniqueDatabase
Enforce a business rule: conditional, cross-field, or needing a lookup — with a friendly message@api.constrainsApp, pre-write
Guard a specific operation (block delete), run a post-write side effect, or read the raw cmd@api.on_hookApp, around op
The rule of thumbField flags for shape → constraints.* when the database itself must guarantee it → @api.constrains for a business rule with a friendly message → @api.on_hook when you need a specific operation, the post phase, or the raw command. The next four sections cover each in turn.

Section 02

02DB-driven — the constraints.* namespace

Import constraints exactly like fields, then declare table constraints as class-body attributes beside the fields they govern. The database enforces them against every writer — the ORM, the data loader, raw SQL.

constraints.Check — a SQL predicate over the row's own columns
from ede.core.kernel import fields from ede.core.kernel import constraints @api.model("logistics.product") class Product(DomainModel): min_qty = fields.Integer(default=0) max_qty = fields.Integer(default=0) # the attribute name (qty_bounds) becomes the DB constraint name qty_bounds = constraints.Check("min_qty <= max_qty", message="min_qty must be ≤ max_qty")
constraints.Unique — composite uniqueness (use fields.X(unique=True) for a single column)
code = fields.Char() org_id = fields.Reference("res.organization") code_per_org = constraints.Unique("code", "org_id", message="code must be unique per organization")

Yes — this is a composite key: the combination is unique

Unique("code", "org_id") constrains the pair (code, org_id) as a whole — not each column on its own. The same code may appear under different organizations, and one organization may hold many codes; only the exact (code, org_id) combination cannot repeat.

#codeorg_idResult
1PROD-AOrg 1INSERTED first row
2PROD-AOrg 2ALLOWED same code, different org
3PROD-BOrg 1ALLOWED same org, different code
4PROD-AOrg 1REJECTED duplicate (code, org_id) → your message
⚠ Not the same as two single-field uniquesMarking code and org_id each unique=True would (wrongly) forbid the same code in two orgs and reuse of an org — rows 2 and 3 above would fail. Composite Unique(...) is the correct tool for "unique per org" scoping. Column order doesn't change the guarantee (the set of columns is what's unique); it only affects lookups that reuse the index.

What you get

AspectBehaviour
EnforcementReal DB CHECK / UNIQUE — holds even if a write bypasses the ORM
On violationRaises ConstraintViolation carrying your message → surfaces as HTTP 422 (a clean error, not a 500)
NamingThe attribute name is the identity → ck_logistics_product_qty_bounds / uq_…_code_per_org
Check inputA SQL expression string only — one row's own columns; no Python, no joins/subqueries
⚠ You must generate a migrationAfter adding a constraints.* declaration, run ede migrate generate --app <app> to emit the named constraint. Never hand-author the migration. Names are capped to Postgres' 63-char limit automatically; a Unique naming a non-existent field fails fast at boot.
When a Check isn't enoughA CHECK can only see the current row's columns. The moment your rule is conditional, spans records, or needs a lookup, it belongs in @api.constrains (next section) — not a Check.

Section 03

03From your declaration to database DDL

When you run ede migrate generate, each constraints.* and field declaration compiles to real DDL. Here is exactly what you write and what the database ends up with.

You write (Python)
code = fields.Char(required=True) org_id = fields.Reference("res.organization") min_qty = fields.Integer() max_qty = fields.Integer() qty_bounds = constraints.Check("min_qty <= max_qty", message="min ≤ max") code_per_org = constraints.Unique("code", "org_id", message="unique per org")
Database gets (generated DDL — SQL)
CREATE TABLE logistics_product ( dbid INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT, record_uuid VARCHAR(36) NOT NULL, code VARCHAR(255) NOT NULL, -- required=True → NOT NULL org_id VARCHAR(36), -- Reference → uuid FK column min_qty INTEGER, max_qty INTEGER, -- … auto columns: created_at_utc, updated_at_utc, revision, … … CONSTRAINT ck_logistics_product_qty_bounds CHECK (min_qty <= max_qty), CONSTRAINT uq_logistics_product_code_per_org UNIQUE (code, org_id), CONSTRAINT fk_logistics_product_org_id_res_organization FOREIGN KEY (org_id) REFERENCES res_organization (record_uuid) ON DELETE RESTRICT );

How each piece maps

You writeBecomes in the database
constraints.Check("min_qty <= max_qty")CONSTRAINT ck_<table>_qty_bounds CHECK (min_qty <= max_qty)
constraints.Unique("code", "org_id")CONSTRAINT uq_<table>_code_per_org UNIQUE (code, org_id)
attribute name qty_boundsconstraint name ck_<table>_qty_bounds (capped to 63 chars)
message="…"nothing — the message is never stored in the DB; it lives in Python and is attached when the DB rejects the write
⚠ Code-driven tools generate NO DDL@api.constrains and @api.on_hook add nothing to the schema — no column, no constraint, no migration. They live only in Python and run at write time. Only field flags and constraints.* change the database.
On an existing tableAdding a constraint later emits an ALTER TABLE … ADD CONSTRAINT … instead of the inline form above (on SQLite it runs via a table rebuild). Either way you get the same named constraint — always via ede migrate generate, never hand-written.

Section 04

04Code-driven — @api.constrains

For business rules the database can't express. Decorate a method with the trigger fields; it runs on create and update, receives the record with the incoming payload already merged, and raises to veto. One declaration — no separate create/update hooks, no manual merge.

Signature — (self, record); record reflects the resulting state
@api.constrains("stage", "partner_id") def _won_needs_partner(self, record) -> None: if record.stage == "won" and not record.partner_id: raise ValueError("a lead cannot be marked won without a partner")
Cross-record — self.env is injected, so you can look up other models
@api.constrains("code") def _unique_active_code(self, record) -> None: clash = self.env.models["crm.lead"].search( [("code", "=", record.code), ("active", "=", True), ("id", "!=", record.id)]) if clash: raise ValueError(f"code {record.code} already used by an active lead")

The contract

AspectBehaviour
Runs oncreate and update from one declaration
Trigger fieldsOn update the check is skipped unless the payload touches one of them; on create it always runs. They also document what the rule depends on.
recordPre-merged: incoming payload value if the field is being written, else the current stored value — so you validate the resulting state, no manual merge
VetoRaise any exception → aborts the write inside its transaction; the message reaches the caller (HTTP 422)
self.envInjected — read other models with env.models[...].search(...)
Why not just write two hooks?@api.constrains is sugar over a pre.create + pre.update hook pair — but it writes the rule once, merges the record for you, and gates on the trigger fields. Reach for raw hooks only when you need the delete op, the post phase, or the raw cmd (next section).
⚠ Pre-write only@api.constrains covers create + update. It does not fire on delete and has no post-write phase — those are @api.on_hook.

Section 05

05Lifecycle hooks — @api.on_hook

The general mechanism underneath everything above. A hook fires around a specific command — pre.{model}.{op} before, post.{model}.{op} after. Pre-hooks raise to veto; post-hooks run side effects after a successful write. Use them when @api.constrains is the wrong shape.

Delete guard — an op @api.constrains can't express
@api.on_hook("pre.crm.lead.delete") def _block_won_delete(self, cmd) -> None: if cmd.record.stage == "won": raise ValueError("won leads are retained for audit — archive instead")
Post-write side effect — runs only after the write succeeds
@api.on_hook("post.crm.lead.update") def _notify_owner(self, cmd) -> None: self.env.emit("crm.lead.changed", {"id": cmd.record.id})

What a hook gives you that a constraint doesn't

CapabilityDetail
Any operationcreate · update · delete · any domain command (pre.crm.lead.qualify)
pre and postpre.* can veto; post.* runs after success (cache busting, events, audit)
Raw cmdFull command: cmd.record (live record; __new__ on pre-create), cmd.payload, self.env
Wildcardspre.*.delete fires on every model's delete — for cross-cutting concerns
Reads excludedsearch / read_one / count / read_group never fire hooks — validation is write-only
⚠ On update, validate the resulting stateRaw hooks hand you cmd.record (current values) and cmd.payload (the changes) separately — merge them before checking, or you'll validate stale data. This merge is exactly the boilerplate @api.constrains removes; prefer it for plain create/update rules.

Section 06

06Putting it together & gotchas

A single model often uses several tools at once — each layer catching what the one above can't. Here's a model that stacks all four, then the traps to avoid.

One model, layered defenses
@api.model("logistics.product") class Product(DomainModel): code = fields.Char(required=True) # shape (field flag) org_id = fields.Reference("res.organization") min_qty = fields.Integer(default=0) max_qty = fields.Integer(default=0) stage = fields.Char(default="draft") qty_bounds = constraints.Check("min_qty <= max_qty", message="min ≤ max") # DB code_per_org = constraints.Unique("code", "org_id", message="unique per org") # DB @api.constrains("stage", "max_qty") # business rule def _launch_needs_stock(self, record) -> None: if record.stage == "launched" and (record.max_qty or 0) <= 0: raise ValueError("a launched product needs a positive max_qty") @api.on_hook("pre.logistics.product.delete") # op guard def _block_launched_delete(self, cmd) -> None: if cmd.record.stage == "launched": raise ValueError("archive a launched product, don't delete it")

Do

  • Give every rule a clear message= — it's what the user sees.
  • Run ede migrate generate after any constraints.* change.
  • List real trigger fields on @api.constrains — they gate + document.
  • Read other models with env.models[...].search() inside the rule.

Don't

  • Put Python logic or a join in a Check — SQL, one row only.
  • Expect @api.constrains to fire on delete — use a hook.
  • Check only the payload on update — validate the merged state.
  • Hand-author a migration for a constraint — always generate it.
Errors surface cleanly everywhereAll four tools raise a plain exception to reject a write. Field/DB constraints and ConstraintViolation and any ValueError you raise map to an HTTP 422 with your message — the same clean shape whether the rule ran in the database or in Python.
