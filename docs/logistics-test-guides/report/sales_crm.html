Section 01

01What Sales & CRM does & how to read this guide

Sales & CRM is the commercial control layer: it captures customer intent, qualifies it, prices it correctly, enforces pricing governance, and hands accepted business to operations — without manual re-keying. Five transactional records carry one deal: crm.inquiry → crm.lead → crm.opportunity → crm.quote (with a versioned crm.quote.version) → crm.handover. Each conversion copies party + routing + commercial context forward.

The five state machines you will observe

Inquiry / lead / opportunity / quote status fields are workflow=True — direct writes raise StageWriteForbidden; transitions flow through env.workflow.transition_by_command. Handover is a plain command-driven state field (8 states).

inquiry   : NEW_PROSPECT → PROSPECT_DISQUALIFIED
lead      : LEAD_QUALIFIED → LEAD_DROPPED
opp       : OPP_PROPOSAL_SENT → OPP_NEGOTIATION → OPP_WON | OPP_LOST
quote     : QUOTE_DRAFT → SUBMITTED → UNDER_APPROVAL → APPROVED → SENT → ACCEPTED | REJECTED | EXPIRED | CANCELLED | LOST
handover  : draft → submitted → under_review → accepted → completed  (↳ returned / escalated / rejected)

Pricing-approval routing

  • low-margin — margin_below_threshold==True (mode×lane×tier floor)
  • sell-below-buy — total_sell_amount < total_cost_amount
  • Payment-term / service-scope / validity-extension rules also route
  • Case lands on sales_crm.sales_manager role-bound users

Multi-leg routing (quote.route)

  • One quote version, N crm.quote.route legs
  • leg_type: origin_haulage · main_carriage · transshipment · destination_haulage
  • Door-to-door with transshipment = 4 legs, one deal
  • Transit days roll up to the version; route summary flows to the handover

Section 04 · Scenario B

04Pricing approval, spot rates & negotiation

Goal: exercise the commercial-governance surface — the approval rules that must route a thin-margin quote, the gate that stops a quote leaking to the customer mid-approval, spot-rate RFQs, and the negotiation-log → revision loop. Role: Sales Rep + Pricing Approver.

#ActionExpected result✔ CheckpointTrace
1Price a quote below the resolved margin floor (Globex = Platinum, SEA lane floor 6%), then Request Approval.The low_margin rule fires (margin_below_threshold==True) and routes the case up the pricing chain — sales manager then pricing approver.Low-margin chain selected, not the default.WS4 low_margin
2Price a line so total_sell_amount < total_cost_amount, then Request Approval.The sell_below_buy rule fires and escalates to the mandatory finance / country-head chain.Sell-below-buy escalation selected.WS4 sell_below_buy
3While the case is still open, attempt Send (crm.quote.send).Refused — "cannot send to the customer while an approval is still open". The quote cannot bypass the approval chain.Send blocked mid-approval.WS5 no-send gate
4On the opportunity, run Request Spot Rate (crm.opportunity.request_spot_rate).A pricing.spot.request is raised carrying related_model="crm.opportunity" + related_id; route / commodity / customer default from the opportunity. Surfaces read-only under spot_request_ids.Spot RFQ linked back to the opportunity.Phase 2 WS3
5On a sent quote, Log Negotiation (crm.quote.log_negotiation) — e.g. negotiation_type="price" + a customer request text.A crm.quote.negotiation row is appended with outcome="pending". Type must be one of price / validity_extension / cargo_change / routing_change / service_addition / payment_term / other.Pending negotiation logged.QAB-03
6Run Revise (crm.quote.revise) — optionally with from_negotiation_id.A new version (version_number+1, status draft) is minted; lines / routes / packages copied; prior version marked superseded; current_version_id re-pointed. A linked pending negotiation auto-resolves to accepted_into_revision.New editable version; prior frozen.QAB-03
7Resolve a standalone negotiation via Resolve Negotiation (crm.quote.resolve_negotiation) with outcome ∈ {accepted_into_revision, declined, withdrawn}.Outcome stamped; revision_version_id required when accepted_into_revision. Re-resolving a resolved row is refused.Outcome recorded once.QAB-03
8Terminal branches: Reject (crm.quote.reject, needs lost_reason_id), Mark Lost (crm.quote.mark_lost), Mark Expired (crm.quote.mark_expired), Cancel (crm.quote.cancel).Stage lands in QUOTE_REJECTED / LOST / EXPIRED / CANCELLED. Reject writes a crm.quote.acceptance (decision_type=rejected) — no handover is created.Terminal reached; reject creates no handover.guard: quote_has_lost_reason

Section 06 · Negative checks

06The guards that must refuse — real error messages

Half of testing a commercial spine is confirming it refuses bad input. Each row below trips a specific guard and states the real error string the command raises. The command must reject — no partial write, no state advance.

#ActionExpected refusal (real message)✔
1convert_to_opportunity on a lead not in LEAD_QUALIFIED.“crm.lead.convert_to_opportunity: lead must be in LEAD_QUALIFIED status”.Blocked
2create_quote on an opportunity with no customer.“…opportunity must have a customer (partner_id) before a quote can be drafted from it.”Blocked
3crm.quote.submit on a quote with no current version.“…quote has no current version — create one first via crm.quote.revise or initial save.”Blocked
4crm.quote.submit on a version with no charge lines.“…the current version has no charge lines — add at least one before submitting.”Blocked

⚠ Workflow vs. command guardsStatus-field refusals differ by layer. A direct write to a workflow=True status raises StageWriteForbidden from the kernel; a workflow guard (opp_has_close_date, opp_lost_has_reason, quote_not_expired, quote_has_lost_reason) raises GuardFailed from the engine; the messages above are the command-handler ValueErrors that run before or instead of a transition. Confirm each surfaces as an error toast, not a silent no-op.
