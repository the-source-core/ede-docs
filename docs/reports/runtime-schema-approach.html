Runtime Schema Upgrade
Retiring the Migration Files

A proposal to stop hand-managing 234 numbered database change-files, and instead let the platform work out what the database needs by comparing it against the models — module by module, in dependency order.
Verdict: Feasible, and cheaper than it sounds — roughly four-fifths of the machinery already exists and runs on every upgrade today. The migration files cover only one step of it. The honest cost is one genuinely new component, one new database table, and the loss of a code-review artefact we would need to replace.

Section 01

01How it works today — and where it breaks

Three words do the heavy lifting in this document, so they are worth pinning down before anything else.

TermIn plain language
ModelThe Python class where a developer declares what a business record looks like — a Partner has a name, a country, a currency. This is the blueprint.
SchemaThe actual shape of the database: which tables exist, which columns they have, how they link to each other. This is the building.
Migration fileA small numbered script recording one change to the building — “add this column”, “create this table”. We currently keep 234 of them.

Today, when a developer changes a model, a tool compares the blueprint to a reference database and writes a new migration file describing the difference. Upgrading a customer database means replaying every file that has not run there yet, in order.

Where that goes wrong

The files are stored per module — 39 separate folders — but they are replayed from one shared list. Each file records only which file came before it in the same folder. Nothing in that record says “the file that creates this table must run before the file that points at it”.

234
Migration files
39
Module folders
25
Unmerged branch ends
51
Cross-module links

With 25 loose ends, the replay order is only partly decided. The rest is settled by the order the module folders happen to be listed in — which changes when a business domain is switched on or off.

⚠ This is not theoretical — it hit us in production toolingA fresh database failed to build because an approvals table tried to link to ir_model before the table existed. It had been latent for months, because a database that is upgraded gradually applies each file the day it is written — so it never tests the ordering at all. Only a brand-new database does.
The root problem in one sentenceThe order is a by-product of how files were authored, not a statement of what the database actually needs — so it can be right today and wrong tomorrow without anyone changing a line of code.

Section 02

02What we already have

The important discovery in this review: we are not proposing to build a new system. We already run a module-upgrade pipeline on every single upgrade. The migration files are one step inside it.

When ede migrate upgrade runs today, it walks the modules in dependency order and performs a series of passes. Only the first uses migration files. Everything after it already works by reading the live code and bringing the database into line — exactly the style of working this document proposes to extend.

Step 1
Database shape
Does the table exist, with the right columns?
Replay 234 migration files (the only file-driven step)
Step 2
Describe the models
What models and fields exist right now?
RegistrySync→ir.model→ir.model.field
Step 3
Register capabilities
What screens, tools and metrics ship?
ViewSync→ToolRegistrySync→KpiRegistrySync→CapabilitySync
Step 4
Load reference data
Are the seeded records present and current?
DataLoader (XML / CSV)→Stable external ids→Orphan cleanup

Steps 2 to 4 are all code-is-truth: they read what the modules declare, compare it with the database, and reconcile the difference. They are re-runnable, they need no numbered files, and they have been running in production for months.

The proposal is narrower than it first appearsWe are asking one question: can Step 1 work the same way as Steps 2, 3 and 4 already do? Not “can we replace our upgrade system” — that system exists and works.

Two assets that make this unusually cheap

A. The blueprint is already a clean data structure HAVE

ModelSchemaSpec already describes every table we own — columns, links, indexes, cross-reference tables, constraints — independent of any database technology. It even records which module contributed each column, which is what makes shared models work.

B. Our test suite already builds from the blueprint PROVEN

All 6,614 automated tests create their database directly from the models — not from the migration files. Building a correct database from the blueprint alone is therefore not a hypothesis. It is what every test run has been doing all along.

Section 04

04The mechanic that makes it work

One design decision does most of the work, and it is the reason the ordering problem from Section 01 does not simply reappear in a new form.

The problem, restated

A link (a foreign key) is a rule saying “this column must point at a row in that other table”. The database refuses to create the rule if the other table does not exist yet. That single rule is what makes ordering matter at all — and it is why our approvals module failed against a table owned by a different module.

The fix: build the walls first, connect them last

Instead of creating each link the moment its column is created, the synchroniser collects them and applies them only after every module in the pass has had its tables and columns created.

Pass 1
Structure
Every module, in dependency order
Tables+Columns→Links & indexes set aside (not applied)
Pass 2
Connections
Now that every table exists
Apply all links→Apply all indexes→Apply “must not be empty” rules
Why this matters more than it looksBy the time any link is applied, every table in the system exists. A module pointing at a table owned by another module is no longer an ordering question — it cannot fail. The class of bug described in Section 01 stops being possible rather than being managed.

The same deferral covers two related cases that also trip up a naive comparison:

CaseWhy it needs deferringHow it is handled
“Must not be empty”Adding a required column to a table that already has rows fails — the existing rows have nothing in it.Add the column, fill existing rows with the declared default, then apply the rule.
IndexesCheap to apply, but pointless before the columns they cover exist.Collected and applied in the same closing pass.
Cross-reference tablesA many-to-many table links two modules and can precede either.Table created in the first pass; both its links deferred to the second.
One rule is deliberately missing from this pageWhat the synchroniser does about things the blueprint no longer contains — and what happens when older code meets a newer database — is a decision in its own right, not a mechanic. It is set out in Section 06.

Runtime Schema Upgrade — Approach5
Section 06

06Two decisions that shape this plan

Both are directions, not open questions. Each one removes work from the plan — and each one carries a condition that has to be respected for that saving to be real.

Decision 1 — PostgreSQL only. No second database engine, anywhere.

Half of this is already done. Platform Change 13 (delivered 08 July 2026) made PostgreSQL the sole production engine and took SQLite out of migration generation. It deliberately stopped short of the rest, because the SQLite path turned out to be load-bearing for the test suite.

PieceStateWhat it covers
Platform Change 13DELIVEREDPostgreSQL is the sole production engine; SQLite removed from migration generation.
Platform Change 14PLANNEDThe remainder: move ~90 test fixture files onto PostgreSQL, then delete the SQLite engine, its settings and every dialect branch left in the codebase.
⚠ The sequencing rule — this is the part that mattersChange 14 must land before the synchroniser is built, not after. Build the synchroniser first and it needs a SQLite strategy for a database engine we are in the middle of deleting — work that would be written, tested, reviewed and then thrown away. Build it second and the synchroniser targets one dialect from its first line.

The cost is real and belongs to Change 14, not to this proposal: it is roughly five times the effort of Change 13, and it changes every contributor's workflow — running the test suite will require a live PostgreSQL instead of an in-memory database. That trade was already accepted when the change was scoped.

What we get in returnThe synchroniser is written against one dialect, with no lowest-common-denominator compromises: native JSONB containment, GIN indexes, full date_trunc, and — decisively — the ability to alter a table's rules after creation, which SQLite cannot do at all. That single capability is what makes converging an existing database possible rather than merely creating a new one.

Decision 2 — add and adjust, but never delete

The synchroniser may create and it may relax. It may never remove. Every case is fixed in advance, so the behaviour is predictable rather than a judgement call:

What the comparison findsActionReasoning
Blueprint has a table the database lacksCREATEThe ordinary case.
Blueprint has a column the database lacksADDAdded, then existing rows filled with the declared default.
A column has become requiredADJUSTBlanks filled first, then the rule applied — never the other way round.
A column is no longer requiredRELAXThe “must not be empty” rule is lifted.
The database has a column the blueprint does notRELAX ONLYThe data stays. Its “must not be empty” rule is lifted so the column stops being mandatory. Nothing is dropped.
The database has a table the blueprint does notLEAVEUntouched entirely — it may belong to a module that is simply switched off.
Why row five is the important oneIt is what makes going backwards safe. Deploy an older version of the code against a newer database and it will not know about the newer columns — so when it saves a record it supplies no value for them. If those columns were still marked mandatory, every save would fail. Lifting that rule is precisely what turns a rollback from a special recovery procedure into ordinary behaviour: the old code simply runs the same comparison against its own older blueprint, and carries on. Data written by the newer version stays where it is, waiting.

Section 07

07Pros — what we gain

Ranked by how much each one is worth to us in practice, not by how impressive it sounds.

#GainWhy it matters here
1A whole class of bug disappearsOrdering failures between modules stop being possible, rather than being detected and worked around. The fix we shipped this week becomes unnecessary code.
2Order follows the dependency graphUpgrade order becomes a statement of what depends on what — the same graph the module loader and data loader already use — instead of a by-product of authoring history.
3Switching domains on or off is safeToday, activating or deactivating a business domain silently reshuffles the upgrade order. Under the proposal it changes only which modules are considered.
4One source of truthModels, tests and customer databases would all derive from the same blueprint. Today the tests use one route and customer databases another — which is precisely why the tests stayed green while a fresh database was broken.
5Adding a field is one editChange the model. No generator run, no generated file to review, no chance of the file and the model disagreeing.
6New customers provision faster and cleanerA new database is built once in its final shape, instead of replaying 234 files including tables that are created and later dropped.
7Self-healingA database that has drifted — a failed upgrade, a manual change — is repaired on the next run, because the comparison simply notices what is missing.
8One database dialectWith PostgreSQL as the only target, the synchroniser is written against real capabilities — altering constraints, native JSONB, GIN indexes — instead of the narrowest behaviour two engines share.
9A smaller repository234 files, 39 folders and their supporting tooling retire. New engineers stop having to learn a revision graph to add a column.
The strategic one is #4The other eight are conveniences. This one closes the gap that let a broken database ship past a fully green test suite — and that gap is a property of having two different ways to build a schema, not of any particular bug.
A bonus worth taking regardless of the decisionThe comparison engine can run in report-only mode. That alone gives us a continuous-integration check that says “this branch would produce a broken fresh database” — the check we do not have today, and the reason our fault stayed hidden for months. It is useful even if we never switch the write path on.

Afterwards it is implied by a model edit — the exact database commands become invisible at review time.A command that prints the exact statements the synchroniser would run, published into the pull request automatically. That is a reasonable trade — but it should be made knowingly, and the printed-statements check in Stage 0 is what makes it acceptable.

The decision gates

Gate A — after Stage 0

Does the checker report nothing to do against a real customer database that is fully up to date?

  • Yes → the comparison engine understands our schema. Continue.
  • No → stop and understand every difference first. This is exactly the information we currently lack.

Gate B — after Stage 2

Running the synchroniser after the existing route, does it make zero changes across every customer database?

  • Yes → the two routes agree. Cutover is safe.
  • No → the blueprint and the files disagree somewhere. Reconcile before Stage 4.
⚠ Only Stage 2 is truly blockedStages 0 and 1 read and record; they do not care which engine is underneath, so they can run in parallel with Change 14. It is the write path that must not be written twice. Sequence the work so Change 14 completes before Stage 2 begins — not before the whole project starts.
Why Stage 0 comes first even if we never continueIt is the missing safety net, not a preparatory step. It is the check that would have caught this week's fault before it reached anyone, and it is the same engine every later stage needs. If the project is paused after Stage 0, we still end up better off than we are today.

Section 10

10Recommendation

Approve Stage 0 now and unconditionally, and schedule Platform Change 14. Decide the rest at Gate A, on evidence we do not currently have.

The case for going ahead

This is a smaller change than it appears. Four-fifths of a module-upgrade pipeline already runs on every upgrade, already reads the live code, and already reconciles the database against it. The blueprint is already a clean, technology-independent data structure. Our entire test suite already builds its database from that blueprint. What remains is to extend a proven mechanism from “create a new database” to “bring an existing one into line”.

The risk that would normally sink this — losing data to an undetected rename — has been measured against our own history and has never occurred in 234 changes.

The case for caution

One cost is permanent: we would trade a change record a reviewer can read for a process a reviewer must trust — acceptable only if the printed-statements check from Stage 0 actually lands and is actually wired into review.

The other is a scheduling dependency rather than a new cost. Going PostgreSQL-only removes the largest build item from this plan, but only if Platform Change 14 is completed before the write path is written. Change 14 is already scoped, already accepted as roughly five times the effort of its predecessor, and currently unscheduled. This proposal does not add that cost — it makes it urgent.

RecommendationProceed to Stage 0 immediately — it is low cost, it is the continuous-integration check we are currently missing, and it is the foundation every later stage builds on. Schedule Platform Change 14 now, in parallel: it is the gate on Stage 2 and it is the long pole. Hold Stages 2–5 at Gate A until the checker has run against real customer databases and we can see, rather than assume, how closely the blueprint and the live schema already agree.
