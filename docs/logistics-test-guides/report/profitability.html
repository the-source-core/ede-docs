Section 01

01What Profitability does & how to read this guide

Profitability is the operational answer to "is this shipment making money?" — a read-friendly roll-up over a shipment's economics that never becomes an accounting system. The atomic unit is the logistics.profitability.charge.line (one revenue/cost pair per charge); the roll-up surface is the logistics.shipment.profitability header. Phase 1 runs entirely on estimated cost + inherited revenue — no finance sync, no invoices, no vendor bills.

The three state vocabularies you will observe

The header carries a lifecycle stage, every adjustment a lifecycle status, and every header a derived margin flag. Watch all three on the Profitability tab.

stage    : estimated → provisional → actual → closed  (Phase 1 stays at estimated)
adj status: draft → pending_approval → approved → applied  |  rejected
margin flag: healthy | warning | critical | negative  (derived from margin_pct vs thresholds)

The two engines behind every number

Roll-up (services/rollup.py)

  • Header stores no hand-entered totals (PRF-BR-02)
  • Sums the charge lines' base-currency amounts
  • Gross profit = revenue − effective cost (actual where synced, else estimated)
  • Fires from charge-line post-create / post-update / pre-delete hooks

Currency (services/currency.py)

  • Resolves revenue→base & cost→base rates (PRF-20)
  • Writes converted_revenue_amount / converted_cost_amount onto the line
  • Single-currency lines convert at rate 1 (identity)
  • Upserts a logistics.profitability.currency.line FX record

Section 03 · Scenario B — the multi-currency deep-dive

03Multi-currency — one margin, many currencies

Goal: prove that a charge sold in one currency and bought in another still rolls up to a single base-currency margin — freight forwarding is inherently multi-currency (sell USD, buy EUR/INR, roll up in the org base). Start: the seeded documentation line — revenue 100 USD, estimated cost 5000 INR, base USD.

docs line: revenue 100 USD ── rate 1.0 ──► converted_revenue 100.00 USD
          cost 5000 INR ── rate 0.012048 ──► converted_cost 60.24 USD  ⇒ profit 39.76 USD
#ActionExpected result✔ CheckpointTrace
1Open the documentation charge line (DOC-FEE) and read its currencies.revenue_currency_id = USD, cost_currency_id = INR, base_currency_id = USD — a genuinely cross-currency line.Revenue & cost currencies differ.PRF-20
2Read its converted_revenue_amount / converted_cost_amount.Revenue converts at rate 1 (already USD) → 100.00; cost converts INR→USD at 0.012048 → 60.24. These base amounts drive the line's profit compute.converted_cost = 60.24 USD.PRF-BR-11
3Open the matching logistics.profitability.currency.line FX record.One FX row per cross-currency line: cost_exchange_rate = 0.012048, exchange_rate_source = res_exchange_rate, rate date, converted amounts, fx_gain_loss_amount = 0 (realised only when actuals sync).FX record captures rate, source & date.PRF-20
4Read the docs line profit_amount.Profit computes in base currency from the converted amounts: 100.00 − 60.24 = 39.76 USD — not 100 − 5000.Profit uses converted, not raw, cost.PRF-BR-05
5recompute the header and confirm the total.The roll-up sums converted base amounts (falling back to raw only for single-currency lines), so the docs cost enters as 60.24 — total est cost stays 3010.24 and margin 27.46%.Converted amount folds into the base total.PRF-BR-02
6Inspect the four USD-only lines (freight / origin / destination / customs).Single-currency lines carry converted_* equal to the raw amounts (rate 1); the roll-up treats them identically.Identity conversion on same-currency lines.PRF-20
✔ Scenario B pass criteriaThe INR cost was resolved to 60.24 USD via the currency engine, stored on both the charge line and its FX record, and folded into a single USD margin — the header never mixes currencies.
⚠ Rate source drives the numberThe applied rate comes from profitability.exchange_rate_source (default res_exchange_rate → latest res.exchange.rate for from→base). If no rate row exists, the engine falls back to identity (rate 1) — a missing FX master silently understates a cross-currency cost. Confirm the rate row exists before trusting the converted total.

Section 04 · Scenario C

04Adjustment lifecycle — approval, apply & audit

Goal: override an inherited amount the auditable way — never by silently editing a charge line (PRF-BR-03). Drive the seeded detention-recovery adjustment (+200 USD on the freight line) submit → approve → apply, then confirm the header re-rolls and the audit ledger records it. Roles: Editor submits; Approver approves.

#ActionExpected result✔ CheckpointTrace
1Open the seeded adjustment demo_adjustment_detention — type revenue_increase, amount 200 USD, status = pending_approval, requires_approval = true.Because profitability.revenue_adjustment_requires_approval is on (default true), the delta sits in pending_approval awaiting sign-off — it has not touched the freight line yet.Line still reads 3200; adjustment pending.PRF-06
2As Approver, dispatch logistics.profitability.adjustment.approve.Status → approved then immediately applied (approve calls apply). The freight revenue_amount becomes 3200 + 200 = 3400; revenue_source flips to manual_adjustment.Freight revenue now 3400; status applied.PRF-06
3Read the adjustment's before_amount / after_amount.Stamped for audit: before 3200, after 3400.Before/after captured on the adjustment.PRF-06
4Read the header totals again.Apply recomputes the roll-up: total revenue rises to 4350, gross profit to 1339.76, margin re-derived — no manual re-roll needed.Header re-rolled after apply.PRF-BR-02
5Open the logistics.profitability.audit.entry trail for the header.A new manual_override entry is appended with the before/after JSON, the reason, and a pointer to the adjustment record.Audit entry written for the apply.PRF-BR-18
6Reject path (separate adjustment): raise a new draft, submit it, then dispatch adjustment.reject.Status → rejected; no charge-line mutation occurs, and a manual_override audit entry records the rejection reason.Reject leaves lines untouched but audited.PRF-06
PRF-BR-18
✔ Scenario C pass criteriaThe +200 delta reached the freight line only after approval, the header re-rolled automatically to GP 1339.76, and both the apply and the reject wrote immutable audit entries — the charge line was never edited directly.
⚠ Approval is config-gatedWhen profitability.revenue_adjustment_requires_approval is off, submit auto-approves and applies in one step (no pending state). Verify the config value before asserting where a freshly-submitted adjustment lands.

Section 05 · Guards

05The guards that must hold

Half of testing a commercially-sensitive surface is confirming it refuses the wrong move. Each row below trips a real ValueError — the message shown is the exact string from the module source.

Adjustment status-order guards

#ActionExpected refusal (verbatim)✔
1Dispatch adjustment.apply on an adjustment that is still pending_approval / draft (not approved).“only an approved adjustment can be applied”Blocked
2Dispatch adjustment.submit on an adjustment whose status is not draft.“only a draft adjustment can be submitted”Blocked
3Dispatch adjustment.approve on an adjustment that is not pending_approval / approved.“only a pending adjustment can be approved”Blocked
4Dispatch adjustment.reject on an adjustment that is not pending_approval.“only a pending adjustment can be rejected”Blocked
5Apply a revenue_increase / cost_increase (etc.) adjustment with no target charge line.“adjustment_type '…' requires a target charge line”Blocked

Ledger & immutability guards

#ActionExpected refusal (verbatim)✔

Honest scope — what Phase 1 does NOT do Actual cost / actual revenue stay 0 (no finance sync); billing_status, cost_status, finance_sync_status, and the variance fields are Phase-2 placeholders. Closure, exceptions, and master/console cost allocation are Phase 2. Leg-wise profitability, AI estimates, and BI/reports are Phase 3. Do not test these here — the enum values exist so later phases emit into them, but no Phase-1 command populates them.
