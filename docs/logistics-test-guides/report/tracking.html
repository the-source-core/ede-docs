Section 01

01What Tracking does & how to read this guide

Tracking answers "where is my cargo?" in customer language. It is a projection: it listens to events that upstream modules already emit and derives tracking.milestone, tracking.timeline.entry, tracking.leg.event, an ETA chain, and exception alerts. It never writes a movement event and never writes shipment status directly — source_event_id is read-only, and status advances are emitted for the shipments module to apply.

The five upstream events Tracking listens to

Nothing here is triggered by a Tracking button — the module is event-driven. These listeners create/activate the activation and rebuild projections.

ede.record.created (logistics.shipment)  → initialise activation (initialized) + auto-subscribe customer
shipment.ready_for_execution       → activate the shipment activation (active) + rebuild
shipment.leg_added_removed        → project milestones from movement events
consolidation.console.confirmed    → console-level activation
equipment.movement.event.recorded  → on-event milestone projection (the truth source)

The state machines you will observe

activation.stage : initialized → active → suspended → closed
milestone.status : planned → completed  |  delayed  |  missed  (also: actual)
exception.status : open → acknowledged → resolved → closed
eta.snapshot    : append-only chain · one is_current=true · original_eta immutable

Five subject levels

  • shipment — the demo direct FCL export
  • house / master — consolidation grain
  • console — grouped console
  • leg — per-leg multimodal projection

The three masters that drive projection

  • milestone.type.master — vocabulary + source_event_codes map
  • exception.code.master — alert / delay / ETA reasons
  • status.mapping.master — milestone → shipment-status advance

02Activation lifecycle & milestone projection

Goal: prove Tracking activates itself from upstream events and projects a customer-facing milestone chain from the movement-event stream — without any Tracking-side data entry. Role: Ops monitor. Start: the Globex shipment activation is already active in demo.

Projection is skipped for inactive subjects.New event advances the projection automatically.TRK-02

⚠ Suspend vs closetracking.activation.suspend pauses projection (stage → suspended) reversibly; close is terminal and is auto-fired when a terminal milestone (DELIVERED) completes (TRK-BR-16). Projections only run while stage=active.

Section 03 · Scenario B

03ETA chain, exception alerts & the email path

Goal: exercise the append-only ETA history, the threshold-driven delay exception, its open→resolve lifecycle, and the customer email — whose delivery is owned by foundation.notifications, not Tracking. Start: the demo carries a published current ETA snapshot and an open MILESTONE_DELAY alert.

#ActionExpected result✔ CheckpointTrace
1Open the ETA snapshot chain for the shipment.The current snapshot shows original_eta=06-27 06:00 (immutable), current_eta=06-27 18:00, eta_delta_hours computed, is_current=true.Original ETA immutable; exactly one current row.TRK-12
2Append a new ETA revision (create another snapshot for the same subject).The pre-create hook copies original_eta forward and sets previous_eta; the post-create hook flips the prior snapshot's is_current to false. History is append-only.Prior snapshot demoted; new one is current.TRK-BR-31/32

4Run Publish (tracking.eta.snapshot.publish) on the current snapshot.is_published=true and published_at stamped. Only published snapshots reach customers (portal is Phase 2).Snapshot marked published.TRK-12
5Open the exception Departure delayed at INMUM; run Acknowledge (tracking.exception.alert.acknowledge).status open → acknowledged.Alert acknowledged.TRK-11
6Run Resolve (tracking.exception.alert.resolve) with a resolution_remarks.status=resolved, resolved_at stamped, remarks saved; an exception_closed audit entry is written.Resolved + audited.TRK-11 · TRK-15

A notification_sent audit entry records it.Email dispatched via notifications; audited.TRK-10

⚠ Delivery ownershipTracking owns the subscription, the event keys, recipient resolution, and template content — not delivery. If email fails, look at foundation.notifications. Phase 1 honours the email channel only; other channels are stored but skipped at send time.
